# Voting System

Монорепозиторий сервиса анонимных опросов для национальной компании, проводящей голосования во время телевизионной рекламы. Backend — обязательная часть тестового задания; frontend — опциональный интерфейс голосования и администрирования.

## Статус проекта

Проект находится на этапе подготовки. В `backend/` и `frontend/` есть конфигурационные заготовки, но работающий API, интерфейс и тесты ещё не реализованы. Описанные ниже сценарии и архитектура — требования и проектное предложение, а не готовые возможности.

В `backend/requirements.in` уже перечислены FastAPI, SQLAlchemy, asyncpg, Alembic, Pydantic и pytest. Файл также содержит зависимости стороннего проекта: перед реализацией список нужно пересмотреть. В `frontend/` есть Dockerfile для Node.js, но отсутствует `package.json`. Вложенные инструкции backend содержат сведения о другом проекте; пути и команды из них требуют сверки с фактической реализацией.

## Задание

Компания размещает минутные ролики на крупнейших телеканалах. Каждый ролик показывает один вопрос и QR-код или ссылку на голосование. Вопрос может предусматривать выбор одного варианта, нескольких вариантов или A/B. Аудитория одного ролика — примерно 100 миллионов человек; голосование происходит в течение минуты.

Сервис должен позволять:

- Зрителю проголосовать анонимно, без регистрации.
- Ограничить повторное голосование на базовом уровне, достаточном для обычного пользователя, без обещания полной защиты от обхода.
- Администратору создавать опросы и просматривать обезличенные результаты.

Результат сдаётся в публичном репозитории GitHub или GitLab. Репозиторий должен содержать описание сервиса, инструкции локального запуска и тестирования, обоснование архитектуры и технологий, а также все артефакты работы с ИИ. Использование ИИ поощряется.

## Предлагаемая архитектура

Для начальной реализации — модульный backend на FastAPI с PostgreSQL. HTTP-слой принимает и валидирует запросы, сервисный слой реализует правила опросов, слой хранения работает с данными через SQLAlchemy и asyncpg. Alembic предназначен для версионирования схемы, pytest — для автоматизированных проверок. Это опирается на существующую заготовку зависимостей; окончательный состав и версии нужно зафиксировать при реализации.

PostgreSQL хранит опросы, варианты ответов и принятые голоса. Транзакции и уникальное ограничение на пару «опрос + идентификатор участника» должны обеспечивать однократный учёт голоса даже при параллельных запросах. Все выбранные варианты одного ответа сохраняются атомарно. Проверка дедупликации отдельным запросом перед записью недостаточна из-за гонок.

Публичный API предоставляет получение активного опроса и отправку ответа. Административный API защищён аутентификацией и предоставляет создание опросов и чтение агрегированных результатов. Администратор получает количества и доли ответов, без идентификаторов участников. Для множественного выбора необходимо явно указать знаменатель процентов: доля участников может суммарно превышать 100%.

### Дедупликация и анонимность

Предлагается выдавать случайный идентификатор браузера в подписанной сервером cookie с атрибутами HttpOnly, Secure в HTTPS-окружении и подходящим SameSite. Голосование требует заранее выданной валидной cookie. В базе хранится производный идентификатор, привязанный к опросу; ключ подписи хранится вне репозитория. Повторная отправка не добавляет новый голос и возвращает определённый контрактом ответ.

Очистка cookie, другой браузер или устройство позволяют обойти такую защиту — это осознанное ограничение базовой дедупликации. IP-адрес не является идентификатором человека: за одним адресом могут находиться многие зрители. Ограничение частоты запросов по IP допустимо как дополнительная мера с учётом общих сетей.

Регистрация, имя, телефон и email зрителя не нужны. Технический идентификатор является псевдонимным; необходимо определить срок его хранения, исключить его и сырые IP из административных результатов, ограничить сбор таких данных в логах.

### Нагрузка

100 миллионов зрителей не означают 100 миллионов голосов. При доле участия `p` средняя нагрузка составляет `100 000 000 × p / 60` голосов в секунду:

| Доля участия | Голоса за минуту | Средняя скорость |
|---|---:|---:|
| 1% | 1 000 000 | ≈ 16 667/с |
| 10% | 10 000 000 | ≈ 166 667/с |
| 100% | 100 000 000 | ≈ 1 666 667/с |

Мгновенный пик может быть выше среднего; чтения опроса, загрузка страницы и повторы добавляют запросы. Эти числа — расчёт сценариев, а не подтверждённая производительность реализации.

Начальная схема с одной БД не подтверждает способность выдержать телевизионную нагрузку. Путь масштабирования: CDN для статики и кешируемых описаний опросов, балансировка stateless API, разделение потока голосов и административных запросов, партиционирование данных и асинхронные агрегаты. Не следует обновлять один общий счётчик при каждом голосе: это создаёт конкуренцию за запись.

При необходимости буферизации потока понадобится надёжная очередь и идемпотентные обработчики. Подтверждать приём можно только после устойчивой записи; необходимо различать «принят в обработку» и «учтён». Такая схема требует отдельного решения о дедупликации, восстановлении после сбоев и допустимой задержке результатов. Добавление очереди само по себе не доказывает нужную пропускную способность.

## Локальный запуск и тестирование

На текущем этапе запустить сервис и выполнить прикладные тесты нельзя: отсутствуют точка входа API, схема БД, миграции, тесты и манифест frontend. Готовой Docker Compose-конфигурации также нет. Имеющиеся заготовки не являются проверенной инструкцией запуска.

До сдачи решения этот раздел необходимо дополнить проверенными командами из чистого клона:

1. Установка зависимостей с указанием версий среды выполнения.
2. Подготовка локальной конфигурации из примера без секретов.
3. Запуск хранилища, применение миграций и настройка администратора.
4. Запуск backend и, если реализован, frontend с адресами API и интерфейсов.
5. Создание опроса, отправка голоса и получение результатов через воспроизводимые HTTP-примеры.
6. Запуск автоматизированных тестов и отдельного нагрузочного сценария.

Минимальные проверки: голос по валидному варианту; запрет вариантов другого опроса; правила одиночного и множественного выбора; несуществующий, ещё не открытый и закрытый опрос; повторная и конкурентная отправка с одним идентификатором; отсутствие доступа к администрированию без авторизации; корректность обезличенных итогов; отсутствие потери подтверждённых голосов при сбое.

Нагрузочный отчёт должен указывать оборудование, конфигурацию, профиль трафика, длительность, достигнутую скорость, задержки p95/p99, ошибки и сверку принятых голосов с результатами. Нельзя экстраполировать локальный тест на 100 миллионов зрителей без оговорок и измерений.

## Артефакты ИИ и работа с Git

Инструкции агентов, skills, использованные промпты, доступные экспорты диалогов, решения и отчёты проверок должны сохраняться в сдаваемом репозитории. Для новых текстовых артефактов можно использовать `docs/ai/`; каталог пока не создан. Секреты и персональные данные перед публикацией удаляются с отметкой о редактировании. Нельзя заявлять о наличии экспортов, которые не были сохранены.

Текущая рабочая ветка — `dev`. На данном этапе коммит содержит только корневые `AGENTS.md` и `Readme.md`; содержимое `backend/` и `frontend/` в него не включается. Перед итоговой сдачей реализация и артефакты ИИ также должны попасть в публичный монорепозиторий.
