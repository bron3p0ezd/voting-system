Что исправлять в первую очередь:

2. Разделить выдачу participant cookie и кэшируемое чтение опроса.
   Сейчас первый GET одновременно формирует JWT-cookie и возвращает опрос; ответы с Set-Cookie плохо подходят для CDN-кэша. Практичнее:
   - POST /participant-sessions — выдаёт secure cookie;
   - GET /polls/{id} — возвращает только публичные данные и может кэшироваться CDN/Redis.
     Это потребует изменения frontend-контракта, но резко уменьшит нагрузку на приложение и БД при наплыве.
3. Оптимизировать запись голоса.
   Сейчас на каждый голос выполняются загрузка опроса с вариантами, вставка votes, вставка vote_selections и commit. Полезные шаги:
   - валидировать тип опроса и допустимые option ID по кэшу;
   - оставить в PostgreSQL атомарный INSERT ... ON CONFLICT DO NOTHING;
   - объединить проверку принадлежности варианта и запись в минимальное число SQL round-trip’ов;
   - сохранить 201 только после commit, как требует текущий контракт.
     Не стоит просто отправлять голос в фон и возвращать 201: это нарушит гарантию устойчивой записи.

5. Настроить пул БД и PostgreSQL вместе.
   Добавьте параметры pool_size, max_overflow, pool_timeout, pool_pre_ping в конфигурацию create_async_engine. Сумма соединений всех worker’ов и реплик не должна превышать безопасный лимит PostgreSQL. Для большого числа коротких транзакций обычно полезен PgBouncer, но его режим и лимиты нужно проверять с asyncpg и нагрузочным тестом.
6. Не писать access log для каждого успешного запроса синхронно в stdout.
   При тысячах RPS это создаёт заметную нагрузку на контейнер и лог-драйвер. Оставьте ошибки и метрики, а успешные access logs семплируйте либо отправляйте асинхронно. Аудит голоса при этом остаётся в БД.
7. Добавить защиту от перегрузки на edge.
   Rate limit и WAF можно применять по комбинации cookie, IP и сигнатур запроса. IP допустим как сигнал для ограничения потока, но не как единственный идентификатор участника — это соответствует текущему требованию анонимности.
8. Разделить чтение и запись.
   Публичный опрос — CDN/Redis; запись голоса — primary PostgreSQL; административные результаты — отдельный кэш/реплика с допустимой задержкой. Это разгружает writer-узел.
9. Тестировать распределённо.
   Один Windows-процесс Locust не годится как доказательство 10k+ RPS. Locust рекомендует master + несколько worker-процессов/машин; один worker обычно использует одно ядро, а на Windows --processes недоступен из-за отсутствия fork. Документация Locust
